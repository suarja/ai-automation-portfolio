# Template CLAUDE.md pour Développeurs

Un fichier `CLAUDE.md` est la **source de vérité centrale** pour Claude Code. Il fournit le contexte, les standards et les règles qui guident l'IA dans votre projet.

## Qu'est-ce qu'un fichier CLAUDE.md ?

- **Emplacement** : Racine de votre projet
- **Format** : Markdown simple
- **Chargement** : Automatique par Claude Code au démarrage
- **Contenu** : Architecture, standards, commandes, règles
- **Stack-agnostic** : Adaptable à React, Vue, Node.js, Python, etc.

## Comment utiliser ce template

1. Copiez le contenu du bloc de code ci-dessous
2. Créez un fichier `CLAUDE.md` à la racine de votre projet
3. Collez le contenu
4. Remplacez les `[PLACEHOLDERS]` par vos informations
5. Committez le fichier dans Git

### Context Engineering Principles

1. **Context is King** - Toujours travailler avec le contexte approprié
2. **Type-First Development** - Types avant implémentation
3. **Change Tracking** - Documenter chaque décision architecturale
4. **Systematic Testing** - Tests automatiques avec Vitest

## Standards de Code

### Naming Conventions

**Files & Folders**
- Components: `PascalCase.tsx` (ex: `UserProfile.tsx`)
- Services: `kebab-case.ts` (ex: `user-service.ts`)
- Utilities: `kebab-case.ts` (ex: `format-date.ts`)
- Types: `kebab-case.types.ts` (ex: `user.types.ts`)
- Tests: `*.spec.ts` (Vitest) ou `*.test.ts`

**Code**
- Functions: `camelCase` (ex: `getUserById`)
- Constants: `UPPER_SNAKE_CASE` (ex: `API_BASE_URL`)
- Types/Interfaces: `PascalCase` (ex: `User`, `ApiResponse`)
- Private functions: `_prefixWithUnderscore` (optionnel)

### Type System & Branded Types

**Utiliser des branded types pour le domain modeling :**

\`\`\`typescript
// lib/types/branded.ts
export type Brand<T, TBrand> = T & { __brand: TBrand };

// lib/types/domain.ts
export type UserId = Brand<string, 'UserId'>;
export type Email = Brand<string, 'Email'>;
export type Timestamp = Brand<number, 'Timestamp'>;

// Usage
interface User {
  id: UserId;
  email: Email;
  createdAt: Timestamp;
}
\`\`\`

**Pourquoi ?** Évite les erreurs subtiles (passer un `ProductId` à une fonction attendant `UserId`).

### Validation at Boundaries

**Toujours valider avec Zod aux points d'entrée :**

\`\`\`typescript
import { z } from 'zod';

const UserSchema = z.object({
  email: z.string().email(),
  name: z.string().min(2),
  age: z.number().int().positive(),
});

// API route / form handler
const validated = UserSchema.parse(input); // Throws si invalide
\`\`\`

### Error Handling Pattern

\`\`\`typescript
// Custom errors pour le domaine métier
export class UserNotFoundError extends Error {
  constructor(userId: UserId) {
    super(\`User \${userId} not found\`);
    this.name = 'UserNotFoundError';
  }
}

// Service layer
export async function getUserById(id: UserId): Promise<User> {
  const user = await db.query(/* ... */);
  if (!user) throw new UserNotFoundError(id);
  return user;
}

// API layer - transform errors
try {
  const user = await getUserById(userId);
  return { success: true, data: user };
} catch (error) {
  if (error instanceof UserNotFoundError) {
    return { success: false, error: 'User not found', status: 404 };
  }
  return { success: false, error: 'Internal error', status: 500 };
}
\`\`\`

## Workflows

### Feature Development (TDD Approach)

1. **Write failing test**
\`\`\`typescript
// services/user-service.spec.ts
import { describe, it, expect } from 'vitest';
import { createUser } from './user-service';

describe('createUser', () => {
  it('should create user with valid email', async () => {
    const user = await createUser({ email: 'test@example.com' });
    expect(user.email).toBe('test@example.com');
  });
});
\`\`\`

2. **Implement minimum code to pass**
3. **Refactor while keeping tests green**
4. **Document architectural decisions if needed**

### Testing Strategy

**Unit Tests** - Pure functions, isolated logic
\`\`\`typescript
// lib/utils/slugify.spec.ts
import { describe, it, expect } from 'vitest';
import { slugify } from './slugify';

describe('slugify', () => {
  it('converts string to URL-safe slug', () => {
    expect(slugify('Hello World!')).toBe('hello-world');
  });
});
\`\`\`

**Integration Tests** - Services with dependencies
\`\`\`typescript
// services/user-service.spec.ts
import { describe, it, expect, beforeEach } from 'vitest';
import { createUser, getUserById } from './user-service';

describe('UserService Integration', () => {
  beforeEach(async () => {
    await resetTestDatabase();
  });

  it('creates and retrieves user', async () => {
    const created = await createUser({ email: 'test@example.com' });
    const retrieved = await getUserById(created.id);
    expect(retrieved).toEqual(created);
  });
});
\`\`\`

## Pièges Communs & Solutions

### TypeScript Gotchas

❌ **Type assertion sans validation**
\`\`\`typescript
const user = data as User; // Unsafe!
\`\`\`

✅ **Runtime validation avec Zod**
\`\`\`typescript
const user = UserSchema.parse(data); // Type + validation
\`\`\`

### Async/Await Anti-patterns

❌ **Await dans boucles (N+1 problem)**
\`\`\`typescript
for (const id of userIds) {
  const user = await getUser(id); // Sequential, slow
}
\`\`\`

✅ **Promise.all pour parallélisme**
\`\`\`typescript
const users = await Promise.all(
  userIds.map(id => getUser(id))
);
\`\`\`

### Database Query Patterns

❌ **N+1 queries**
\`\`\`typescript
const users = await db.user.findMany();
for (const user of users) {
  user.posts = await db.post.findMany({ where: { userId: user.id } });
}
\`\`\`

✅ **Eager loading**
\`\`\`typescript
const users = await db.user.findMany({
  include: { posts: true }
});
\`\`\`

## Règles de Comportement IA

### Ce que Claude DOIT faire

✅ **Type Safety First**
- Définir les types AVANT l'implémentation
- Utiliser branded types pour domain models
- Valider avec Zod aux boundaries (API, forms, external data)

✅ **Test Coverage**
- Proposer tests unitaires pour fonctions utilitaires
- Tests d'intégration pour services avec dépendances
- Suivre pattern `describe` > `it` avec Vitest
- Viser >80% coverage sur code critique

✅ **Documentation Inline**
- JSDoc pour fonctions publiques
- Commenter les décisions non-évidentes
- Mettre à jour CLAUDE.md si changement architectural

✅ **Error Handling Robuste**
- Try-catch aux points d'entrée (API, event handlers)
- Custom errors pour cas métier
- Logging approprié (structured logging en production)

### Ce que Claude NE DOIT PAS faire

❌ **Ignorer la validation**
- Ne JAMAIS accepter input utilisateur sans validation Zod
- Ne pas utiliser `any` sans justification explicite

❌ **Créer des dépendances circulaires**
- Vérifier les imports avant d'ajouter
- Services ne doivent pas importer de UI components

❌ **Patterns obsolètes ou non-idiomatiques**
- Éviter callbacks quand async/await possible
- Pas de `var`, toujours `const`/`let`
- Pas de `@ts-ignore` sans commentaire explicatif

❌ **Tests insuffisants**
- Ne pas implémenter de logique métier sans tests
- Ne pas modifier de code critique sans vérifier les tests

## Décisions Architecturales (ADRs)

### ADR-001: Branded Types pour Type Safety

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
TypeScript permet confusion entre types primitifs similaires (userId vs productId tous deux `string`).

**Decision:**
Utiliser branded types pour tous identifiants et valeurs métier.

**Consequences:**
- ✅ Erreurs de type détectées à la compilation
- ✅ Documentation self-evident du domaine
- ⚠️ Légère verbosité, nécessite helpers

### ADR-002: Vitest pour Testing

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
Besoin d'un test runner rapide avec excellent support TypeScript.

**Decision:**
Vitest comme framework de test principal.

**Consequences:**
- ✅ 10-20x plus rapide que Jest
- ✅ ESM natif, config minimale
- ✅ API compatible Jest (migration facile)
- ⚠️ Ecosystem plus récent

### ADR-003: Zod pour Validation Runtime

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
TypeScript types disparaissent à runtime. Besoin validation des inputs externes.

**Decision:**
Zod pour validation + inference de types.

**Consequences:**
- ✅ Single source of truth (schema → types)
- ✅ Messages d'erreur clairs
- ✅ Validation composable
- ⚠️ Bundle size légèrement plus gros

# Template CLAUDE.md pour Développeurs

Un fichier `CLAUDE.md` est la **source de vérité centrale** pour Claude Code. Il fournit le contexte, les standards et les règles qui guident l'IA dans votre projet.

## 🚀 Installation et Mise en Place

### Étape 1 : Installer Claude Code (CLI)

Si vous n'avez pas encore installé Claude Code, voici comment procéder :

```bash
# Installation via npm (recommandé)
npm install -g @anthropics/claude-code

# Ou via Homebrew (macOS/Linux)
brew install anthropics/tap/claude-code
```

Après l'installation, vérifiez que Claude Code est installé :

```bash
claude --version
```

### Étape 2 : Initialiser Claude dans votre projet

Naviguez vers la racine de votre projet et initialisez Claude Code :

```bash
# Naviguez vers votre projet
cd /chemin/vers/votre/projet

# Initialisez Claude Code
claude init
```

Cette commande crée un fichier de configuration `.claude/config.json` dans votre projet.

### Étape 3 : Créer et configurer votre fichier CLAUDE.md

Deux approches possibles :

**Option A : Utiliser le template de cette page**

1. Copiez le template complet ci-dessous (utilisez le bouton "Copier" sur le bloc de code)
2. Créez un fichier `CLAUDE.md` à la racine de votre projet
3. Collez le contenu copié
4. Remplacez tous les `[PLACEHOLDERS]` par vos informations spécifiques

```bash
# À la racine de votre projet
touch CLAUDE.md
# Collez le contenu du template et personnalisez-le
```

**Option B : Utiliser un template depuis un fichier existant**

Si vous avez déjà un fichier `CLAUDE.md` d'inspiration (par exemple, téléchargé depuis cette ressource) :

```bash
# Copiez le fichier template dans votre projet
cp ~/Downloads/CLAUDE-TEMPLATE.md ./CLAUDE.md

# Ou pointez Claude vers un template d'inspiration
claude init --template ~/Documents/Templates/CLAUDE-TEMPLATE.md
```

### Étape 4 : Personnaliser le template

Remplacez tous les placeholders dans votre `CLAUDE.md` :

- `[NOM_DU_PROJET]` → Le nom de votre projet (ex: "TaskManager Pro")
- `[Framework + version]` → Votre stack technique (ex: "React 18.2")
- `[Database]` → Votre base de données (ex: "PostgreSQL 15")
- `[ÉQUIPE/PERSONNE]` → Qui maintient ce fichier (ex: "Équipe Frontend")
- `[EMAIL/SLACK]` → Canal de communication pour questions

**Exemple de personnalisation :**

```markdown
## Aperçu du Projet

**Nom :** TaskManager Pro
**Type :** Web App
**Stack :** React 18 + TypeScript + Express 4
**Objectif :** Application de gestion de tâches collaborative pour équipes distribuées
```

### Étape 5 : Lancer Claude Code

Une fois votre `CLAUDE.md` configuré, démarrez Claude Code :

```bash
# Démarrez une session interactive
claude

# Ou demandez directement quelque chose
claude "Quelle est l'architecture de ce projet ?"
```

Claude Code va **automatiquement charger** votre fichier `CLAUDE.md` et l'utiliser comme contexte pour toutes les interactions.

### Étape 6 : Vérifier que ça fonctionne

Testez que Claude a bien compris votre contexte :

```bash
claude "Résume l'architecture de ce projet"
claude "Quels sont les standards de code à respecter ?"
claude "Comment créer un nouveau service avec tests ?"
```

Si Claude répond précisément en se basant sur votre `CLAUDE.md` → ✅ **Tout fonctionne !**

### Étape 7 : Committez dans Git

N'oubliez pas de versionner votre fichier :

```bash
git add CLAUDE.md
git commit -m "docs: add CLAUDE.md for AI context engineering"
git push
```

## Architecture

### Context Engineering Principles

1. **Context is King** - Toujours travailler avec le contexte approprié
2. **Type-First Development** - Types avant implémentation
3. **Change Tracking** - Documenter chaque décision architecturale
4. **Systematic Testing** - Tests automatiques avec Vitest

### Folder Structure

\`\`\`
project-root/
├── src/
│   ├── components/        # UI components
│   ├── services/          # Business logic (stack agnostic)
│   ├── lib/
│   │   ├── db/            # Database layer
│   │   ├── types/         # TypeScript types
│   │   └── utils/         # Pure utility functions
│   ├── hooks/             # Custom hooks (si React/Vue)
│   └── __tests__/         # Test files
│       ├── unit/
│       ├── integration/
│       └── e2e/
├── docs/
│   ├── decisions/         # ADRs (Architectural Decision Records)
│   └── README.md          # Project documentation
└── [config files]
\`\`\`

### Architectural Principles

**Separation of Concerns**
- UI layer (`components/`) ne contient QUE de la présentation
- Business logic isolée dans `services/`
- Data access centralisé dans `lib/db/`

**Dependency Direction**
\`\`\`
UI → Services → Database
  ↓
Types (shared across all layers)
\`\`\`

## Standards de Code

### Naming Conventions

**Files & Folders**
- Components: `PascalCase.tsx` (ex: `UserProfile.tsx`)
- Services: `kebab-case.ts` (ex: `user-service.ts`)
- Utilities: `kebab-case.ts` (ex: `format-date.ts`)
- Types: `kebab-case.types.ts` (ex: `user.types.ts`)
- Tests: `*.spec.ts` (Vitest) ou `*.test.ts`

**Code**
- Functions: `camelCase` (ex: `getUserById`)
- Constants: `UPPER_SNAKE_CASE` (ex: `API_BASE_URL`)
- Types/Interfaces: `PascalCase` (ex: `User`, `ApiResponse`)
- Private functions: `_prefixWithUnderscore` (optionnel)

### Type System & Branded Types

**Utiliser des branded types pour le domain modeling :**

\`\`\`typescript
// lib/types/branded.ts
export type Brand<T, TBrand> = T & { __brand: TBrand };

// lib/types/domain.ts
export type UserId = Brand<string, 'UserId'>;
export type Email = Brand<string, 'Email'>;
export type Timestamp = Brand<number, 'Timestamp'>;

// Usage
interface User {
  id: UserId;
  email: Email;
  createdAt: Timestamp;
}
\`\`\`

**Pourquoi ?** Évite les erreurs subtiles (passer un `ProductId` à une fonction attendant `UserId`).

### Validation at Boundaries

**Toujours valider avec Zod aux points d'entrée :**

\`\`\`typescript
import { z } from 'zod';

const UserSchema = z.object({
  email: z.string().email(),
  name: z.string().min(2),
  age: z.number().int().positive(),
});

// API route / form handler
const validated = UserSchema.parse(input); // Throws si invalide
\`\`\`

### Error Handling Pattern

\`\`\`typescript
// Custom errors pour le domaine métier
export class UserNotFoundError extends Error {
  constructor(userId: UserId) {
    super(\`User \${userId} not found\`);
    this.name = 'UserNotFoundError';
  }
}

// Service layer
export async function getUserById(id: UserId): Promise<User> {
  const user = await db.query(/* ... */);
  if (!user) throw new UserNotFoundError(id);
  return user;
}

// API layer - transform errors
try {
  const user = await getUserById(userId);
  return { success: true, data: user };
} catch (error) {
  if (error instanceof UserNotFoundError) {
    return { success: false, error: 'User not found', status: 404 };
  }
  return { success: false, error: 'Internal error', status: 500 };
}
\`\`\`

**Unit Tests** - Pure functions, isolated logic
\`\`\`typescript

## Pièges Communs & Solutions

### TypeScript Gotchas

❌ **Type assertion sans validation**
\`\`\`typescript
const user = data as User; // Unsafe!
\`\`\`

✅ **Runtime validation avec Zod**
\`\`\`typescript
const user = UserSchema.parse(data); // Type + validation
\`\`\`

### Async/Await Anti-patterns

❌ **Await dans boucles (N+1 problem)**
\`\`\`typescript
for (const id of userIds) {
  const user = await getUser(id); // Sequential, slow
}
\`\`\`

✅ **Promise.all pour parallélisme**
\`\`\`typescript
const users = await Promise.all(
  userIds.map(id => getUser(id))
);
\`\`\`

### Database Query Patterns

❌ **N+1 queries**
\`\`\`typescript
const users = await db.user.findMany();
for (const user of users) {
  user.posts = await db.post.findMany({ where: { userId: user.id } });
}
\`\`\`

✅ **Eager loading**
\`\`\`typescript
const users = await db.user.findMany({
  include: { posts: true }
});
\`\`\`

## Règles de Comportement

### Ce que tu dois faire

✅ **Type Safety First**
- Définis les types AVANT l'implémentation
- Utilise des branded types pour les domain models
- Valide avec Zod aux boundaries (API, forms, external data)

✅ **Test Coverage**
- Propose des tests unitaires pour les fonctions utilitaires
- Crée des tests d'intégration pour les services avec dépendances
- Suis le pattern `describe` > `it` avec Vitest
- Vise >80% coverage sur le code critique

✅ **Documentation Inline**
- Ajoute JSDoc pour les fonctions publiques
- Commente les décisions non-évidentes
- Mets à jour CLAUDE.md si changement architectural

✅ **Error Handling Robuste**
- Ajoute try-catch aux points d'entrée (API, event handlers)
- Crée des custom errors pour les cas métier
- Utilise un logging approprié (structured logging en production)

### Ce que tu ne dois PAS faire

❌ **Ignorer la validation**
- N'accepte JAMAIS d'input utilisateur sans validation Zod
- N'utilise pas `any` sans justification explicite

❌ **Créer des dépendances circulaires**
- Vérifie les imports avant d'ajouter du code
- Les services ne doivent pas importer de UI components

❌ **Patterns obsolètes ou non-idiomatiques**
- Évite les callbacks quand async/await est possible
- N'utilise pas `var`, utilise toujours `const`/`let`
- N'utilise pas `@ts-ignore` sans commentaire explicatif

❌ **Tests insuffisants**
- N'implémente pas de logique métier sans tests
- Ne modifie pas de code critique sans vérifier les tests

### ADR-001: Branded Types pour Type Safety

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
TypeScript permet confusion entre types primitifs similaires (userId vs productId tous deux `string`).

**Decision:**
Utiliser branded types pour tous identifiants et valeurs métier.

**Consequences:**
- ✅ Erreurs de type détectées à la compilation
- ✅ Documentation self-evident du domaine
- ⚠️ Légère verbosité, nécessite helpers

### ADR-002: Vitest pour Testing

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
Besoin d'un test runner rapide avec excellent support TypeScript.

**Decision:**
Vitest comme framework de test principal.

**Consequences:**
- ✅ 10-20x plus rapide que Jest
- ✅ ESM natif, config minimale
- ✅ API compatible Jest (migration facile)
- ⚠️ Ecosystem plus récent

### ADR-003: Zod pour Validation Runtime

**Date:** [YYYY-MM-DD]
**Status:** ✅ Accepted

**Context:**
TypeScript types disparaissent à runtime. Besoin validation des inputs externes.

**Decision:**
Zod pour validation + inference de types.

**Consequences:**
- ✅ Single source of truth (schema → types)
- ✅ Messages d'erreur clairs
- ✅ Validation composable
- ⚠️ Bundle size légèrement plus gros

## 💬 Besoin d'aide ?

**Questions fréquentes :**

**Q : Mon CLAUDE.md est trop long, Claude ne le lit pas en entier ?**
R : Claude Code charge tout le fichier. Si trop verbeux, split en plusieurs fichiers ou utilisez des monorepos patterns.

**Q : Dois-je tout mettre dans CLAUDE.md ?**
R : Non. Mettez l'essentiel : architecture, standards, pièges. Pas besoin de documenter chaque fonction.

**Q : Mon équipe n'utilise pas Claude, est-ce quand même utile ?**
R : Oui ! CLAUDE.md sert aussi de documentation vivante pour les humains. C'est un excellent README technique.

**Q : À quelle fréquence mettre à jour ?**
R : Mettez à jour à chaque décision architecturale majeure ou nouveau piège découvert. Minimum : revue mensuelle.
